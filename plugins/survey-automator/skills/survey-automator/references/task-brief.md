# Task 2 — Brief to survey

The user provided a survey brief (typically Word or PDF) and wants it implemented as Survey Automator JSON. Completeness and fidelity to the brief's wording are the primary success criteria.

## Task-specific rules

- **Read every question in the brief and create one survey item per brief question. Do not skip, merge, or summarize.** After drafting, count brief questions vs. survey items and confirm they match.
- **Use the brief's exact wording.** Copy question text and answer option text verbatim into `surveyText` and answer `text` fields. Do not paraphrase, "improve", or shorten. If the brief provides both a short label and a full question, put the label in `text` and the full question in `surveyText`. If only one is provided, use it for `surveyText` and derive a brief reporting label for `text`.
- **Use the brief's question IDs** (`1`, `2`, `Q1`, etc.) directly as the `id` field. Do not invent your own naming scheme. If the brief uses no IDs, fall back to descriptive ids.
- **Flow control.** If the brief mentions screening criteria (e.g. "exclude respondents who…", "only customers who purchased in the last year", "if X then end survey") or consistency/validation errors between answers (e.g. "if employed full-time but reports 0 hours, flag", "must be 18+"), read `references/flow-control.md` before drafting — these are implemented as `screenout` and `error` items.
- **Survey messages.** If the brief specifies any end-of-flow copy (thank-you wording, redirect URL after completion, screened-out copy, closed-survey wording, password-failure wording, repeat-respondent wording), implement it under the top-level `surveyMessages` object per `references/messages.md`. Set only the keys the brief covers — omit the rest so the platform shows its defaults. **If the survey contains any `screenout` items, also set `screenedOut`** even when the brief is silent on it — the brief-driven `screenout` items deserve survey-appropriate exit copy. The brief-driven equivalent of the prompt-task's "always include `surveyComplete`" rule does *not* apply: only include `surveyComplete` when the brief calls for custom thank-you copy.
- **Section headers.** If the brief is organized into sections, mirror that structure with `header` items using the brief's section names. If the brief is a flat list, you may add appropriate section headers only if it improves navigation — don't impose structure where the brief intends none. Apply `pagebreak: true` to section headers as standard.
- **Intro header.** If the brief contains an introduction or preamble for respondents, put it in an opening `header` item (survey name in `text`, intro in `comment`, no pagebreak). If the brief has no intro, omit the intro header — don't invent one.
- **No example responses by default.** Brief-driven surveys are usually destined for real fieldwork. Only generate responses if the user explicitly asks; then follow `references/response-generation.md` and `references/format-data.md`.
- **Key order in the output JSON: when `responses` is included, it must be the last top-level key.** Put `questions` first, then `surveyMessages` and/or `participants`, then `responses` last. The validator rejects files where `responses` is followed by any other top-level key.
- **After delivering the first draft, ask clarifying questions** about anything ambiguous in the brief — unclear scales, missing min/max constraints, ambiguous question types. Do this *after* the draft, not before.

## Authoring questions

Read `references/format-core.md` and `references/format-questions.md` for the full spec, and **mimic `references/example.json` for idiom**. The high-leverage points:

- **Question types** are `single`, `multiple`, `open`, `header`. **There is no `type: "matrix"`** — matrices are `type: "single"` with a `rows` array.
- **Matrix row ids** MUST be `<QuestionId>.<N>`. For a single standalone scale (e.g. one Likert), still model it as a matrix with one anonymous row whose `id` is `<QuestionId>.1` and no `text` field.
- **`scale: "Ordinal"` whenever the answers have an order.** Any scaled question or grid whose answer options form an ordered sequence — numeric rating points, agreement, satisfaction, frequency, likelihood, and similar — MUST set `scale: "Ordinal"` (capital O), regardless of whether the brief uses polarity anchors or per-option labels. Omit `scale` only when the options are genuinely unordered categories. The validator enforces this whenever answers carry `Positive`/`Negative` tags.
- **Scale anchors:** tag low-end answers with `type: "Negative"`, high-end with `type: "Positive"`, "don't know"/"N/A" with `type: "DontKnow"`. On every Likert-style question — anchored or descriptively labelled — give each answer a numeric `symbolText` (`"1"`, `"2"`, …; `"?"` for DontKnow) so compact renderings work. **Use `scaleLeft`/`scaleRight` (and `scaleDK`) whenever the scale has two polarities** — i.e. answer options are points on a spectrum between a low and a high anchor (the standard, preferred Likert pattern). **Omit them when the brief gives each option its own descriptive label** (e.g. "Strongly disagree" through "Strongly agree") — the labels do the anchoring themselves.
- **"Other / please specify"**: an answer with `type: "Other"` plus an answer with `type: "Open"`, `id: "0"` and `connectedTo: "<id>"` referencing the Other answer, listed first in `answers`.
- **`DontKnow`** is valid on any closed-list question, not just scales. On scale questions that use `symbolText` on other answers, the `DontKnow` answer takes `symbolText: "?"`; on polarity scales (those using `scaleLeft`/`scaleRight`) the `text` is also `"?"`. On non-scale closed lists, use a readable `text` like `"Don't know"` or `"Not sure"` with no `symbolText`.
- **`min`/`max`:** unless the brief says otherwise, set `min: 1` on every question except open comment fields. On `multiple`, set `max` only for a stated limit ("select up to 3" → `max: 3`); otherwise leave `max` out (no limit) — never set it to the number of answers.
- **Open questions** with numeric input use `dataType: "integer"`.
- **Open ends:** all open-ended questions should have a `placeholder` — write a relevant one if missing in the brief. Always choose an appropriate `charWidth` and `charHeight` for the question.
- **Headers** have only `id`, `type`, `text`, optionally `comment` and `pagebreak`.
- **Calculated variables** (derived, grouped or recoded variables, coded open ends, period or category breakdowns) are added only when the user asks for them. Then read `calculated-variables.md` and write the short forms shown there.
- **Rich texts**: plain strings with `<b>`/`<i>`/`<u>`/`<a href>`/`<ul><li>` and bookmarks are covered in `format-questions.md`. Read `texts.md` only when a text needs a picture, video, document link, conditional text, the typed text of an open answer, or HTML code.
- **`interface`** controls how options are rendered. Absent interface means default radios or checkboxes — the right choice when no other rule applies. Use `"buttons"` whenever *all* answer labels are short, including on single-select grids with ≤5 options — and in particular always use `"buttons"` when every label is under 15 characters and there are 6 or fewer answers. Use `"dropdown"` for long ordered single-select lists (~30+). Use `"vertical"` on grids when any answer label is long. For polarity Likert grids, use `scaleLeft`/`scaleRight`/`scaleDK` and absent interface. When you use `"dropdown"`, always add a relevant question-level `placeholder` for the empty state (e.g. `"Select a country…"`, `"Choose your region…"`) — phrase it to match what the list contains. **Use `slider` or `dragdrop` only when the user or brief explicitly asks for a slider or drag-and-drop**; use `ranking` (a `single` grid whose answers are the rank positions) when respondents should rank items. Never choose `alpha` or `numeric` — use `vertical` or `buttons`. Before writing any of these, read `grid-interfaces.md`.

When in doubt, mimic the example rather than reasoning from these rules.
